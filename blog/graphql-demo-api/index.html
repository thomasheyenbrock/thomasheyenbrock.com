The Ultimate GraphQL Demo API

I have spent a lot of time in my career working on GraphQL tooling. I built the second major version of GraphiQL, and at Stellate I have been involved with GraphQL caching for over two years.

I found myself coming back to implementing simple GraphQL APIs with very specific features to aid in development and testing. And while it became relatively easy for me to do so, it might not be as easy for others.

The Status Quo

I started looking at existing open GraphQL APIs that are commonly used for testing and showcasing the capabilities of GraphQL. And there do exist a bunch:

  • SWAPI (Star Wars API)
  • Countries API
  • Rick and Morty API

All of the above succeed in showing how to query data using GraphQL. But that is not all that GraphQL can do. Concretely, these APIs fall short on:

  • Support for sending mutations or subscriptions.
  • Having Interface Types or Union Types as part of their schema.
  • Implementing common patterns in GraphQL schema design (global identifiers, connections, error unions, etc.)
  • Examples for authorization
  • Security filters (depth limits, token limits, alias limits, etc.)
  • Support for work-in-progress GraphQL features that are not yet part of the official specification (@defer, @stream, @oneOf, etc.)

For each of the above, I have created a dedicated GraphQL API in the past. And I don't want to repeat doing it over and over.

So I created one to rule them all.

Graph of Thrones API

I picked the popular Game of Thrones TV series as my genre of choice. Mainly because I liked the series, but also because there's lots of content to build an extensive API around.

Let's look at what this API can do.

All kinds of schema types

While many GraphQL Demo APIs limit their schema to using Object Types, the schema of the Graph of Thrones API contains all kinds of types, in particular Interface Types, Union Types, Input Types, Enum Types, and even custom Scalar Types.

There exist many different locations in the Game of Thrones Universe, and locations can be of different kinds: Settlements, Regions, Continents, and many more. Mutations and Subscription

While queries are the most-used operation type in GraphQL, mutations and subscriptions are an essential part of the specification as well.

However, they are not as trivial to implement as queries. A mutation implies that the server is stateful or there is some sort of storage that persists changes to data. Subscriptions are even more complex because they need additional functionality to stream back incremental payloads to the client.

Common schema design patterns

Over the years, a lot of patterns emerged for how to design scalable GraphQL schemas. The Graph of Thrones API supports most of them.

Global Identifiers

This pattern was made popular by Relay. It requires all entities to have a unique id field by implementing a Node interface. This allows fetching individual entities by those identifiers through the node and nodes query root fields.

Connection Fields

Another popular pattern that emerged through Relay was using so-called connection fields. They are an advanced way of dealing with long lists that allows the client to efficiently paginate the list, meaning only fetching subsets of the complete list.

Error Unions

Error handling is a contested topic in GraphQL. A popular pattern that emerged was to encode error information inside the schema using Union Types. The GraphQL of Thrones API applies this patterns to its mutations.

Upcoming GraphQL Features

There are some exciting proposals to extend the GraphQL specification with new functionality. Some of those proposals are already being used in production today, so the Graph of Thrones API makes sure to implement them.

Incremental Delivery

While subscriptions are already part of the GraphQL specification, incremental delivery is also coming to queries and mutations with the new @defer and @stream directives.

The @defer directive allows you to mark a fragment to be delivered incrementally, meaning it will be sent only after all the non-deferred fields have been resolved.

The @stream directive allows you to mark fields that return a list so that individual list items will be sent by the server whenever they are resolved, without having to wait for the complete list.

@oneOf Input Directive

When using multiple arguments for a single field, you sometimes want to enforce that these arguments are set mutually exclusive. In other words, you want to prevent two non-compattible arguments from being sent at the same time. This is exactly what the proposal for a @oneOf schema directive solved.

The Graph of Thrones API implements this directive for Input Types that are used to fetch individual entities using different unique properties.
